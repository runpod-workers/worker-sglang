# SGLang v0.5.15.post1 Worker Upgrade Design

## Objective

Upgrade the RunPod SGLang worker from its v0.5.9-era integration to SGLang
v0.5.15.post1 while preserving the official worker's request and deployment
shape. The supported runtime is CUDA 13.0 on NVIDIA H100 and H200 GPUs.

## Scope

- Pin both full and runtime base images to `lmsysorg/sglang:v0.5.15.post1`
  variants.
- Keep the RunPod native and OpenAI-compatible request formats.
- Keep stable worker-facing environment variables such as `MODEL_NAME` and
  `TENSOR_PARALLEL_SIZE`, but translate them to current canonical SGLang CLI
  flags.
- Remove obsolete or deprecated SGLang settings instead of maintaining
  compatibility aliases.
- Update documentation, compose/bake configuration, Hub metadata where
  applicable, and automated tests.
- Do not redesign the official worker architecture or add unrelated features.

## Runtime and Image Design

The default image will use `lmsysorg/sglang:v0.5.15.post1`. The runtime bake
target will use `lmsysorg/sglang:v0.5.15.post1-runtime`. Both tags exist in the
official image registry and provide the CUDA 13 generation selected for this
upgrade.

Version selection will be explicit and centralized in Docker build arguments
and bake configuration. Floating `latest` tags will not be used so that CI/CD
rebuilds are reproducible.

## Engine Argument Design

`engine.py` will continue to construct an argument vector and launch
`python3 -m sglang.launch_server`. The mapping will use current v0.5.15.post1
canonical flags.

Key migrations include:

- Parallelism flags use `--tp-size`, `--dp-size`, `--pp-size`, and `--ep-size`.
- NSA backend settings are replaced by DSA settings using
  `--dsa-prefill-backend` and `--dsa-decode-backend`.
- The deprecated aggregate CUDA Graph switch is replaced by explicit decode
  and prefill backend settings.
- Removed `ENABLE_FLASHINFER_MLA` and `ENABLE_OVERLAP` mappings are not
  retained.
- Current prefill/decode attention, MoE, speculative decoding, metrics, LoRA,
  and scheduling settings relevant to H100/H200 deployments are exposed using
  explicit environment-to-argument mappings.
- Multi-value arguments such as LoRA paths are encoded as separate argv items;
  no shell parsing is used.

The engine will fail fast for invalid numeric worker settings and will surface
an early SGLang subprocess exit during readiness polling. SGLang remains the
source of truth for validating model-specific combinations.

## Request Handling

The worker retains the current four request paths:

1. Explicit OpenAI route forwarding.
2. Chat completion requests inferred from `messages`.
3. Text completion requests inferred from `prompt`.
4. Native SGLang generation requests using `text`, `input_ids`, or
   `input_embeds`.

Non-success HTTP responses will be returned as structured worker errors. Both
streaming and non-streaming behavior will remain covered by tests. The upgrade
will not introduce a new public request schema.

## Verification

Local verification will cover:

- Exact command generation for representative environment variables.
- Absence of removed/deprecated SGLang flags.
- Process startup, readiness, early-exit, and shutdown behavior with mocked
  subprocess and HTTP boundaries.
- RunPod native and OpenAI-compatible routing, streaming, and upstream error
  handling.
- Python syntax and unit tests.
- Docker Compose/Bake rendering and official base-image tag availability.

GPU validation will use the existing deployment automation:

1. Push the updated repository.
2. Wait for CI/CD image build and RunPod deployment completion.
3. Confirm the newly deployed revision is ready.
4. Run health/models, native generation, chat completion, streaming, and
   parser-related smoke tests.
5. On failure, update the code, push again, and repeat.

The official RunPod MCP can update endpoints, invoke jobs, and poll results,
but it does not expose worker logs or build artifacts. Failures visible in job
results can participate in the automatic repair loop. Container-startup or
CUDA-initialization failures that only appear in worker logs require the
RunPod console or another log channel.

## Repository Constraint

The local `worker-sglang` directory is not an independent Git checkout, and
the enclosing workspace repository currently has a broken nested-repository
status traversal. Implementation can be completed and tested in this folder,
but commit, push, CI/CD monitoring, and RunPod validation require a valid Git
repository/remote and a connected, authenticated RunPod MCP in the execution
environment.

## Acceptance Criteria

- All Docker build paths resolve to SGLang v0.5.15.post1 images.
- No removed or intentionally deprecated SGLang flags are emitted.
- Stable official-worker environment settings generate valid canonical
  v0.5.15.post1 arguments.
- Local automated tests pass without requiring a GPU.
- Documentation describes CUDA 13.0, H100/H200, the pinned engine version,
  and the supported configuration surface.
- Once repository and RunPod access are connected, the deployed H100/H200
  worker passes the defined smoke tests.
